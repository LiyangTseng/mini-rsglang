Write docs/benchmarks/baseline-profile.md by hand (D-12, D-14: hand-written afterward, reading from the JSON). Every number in it comes from the JSON, and nothing is estimated. Use exactly these headings, in this order:
- `# Python Frontend Baseline Profile`
- `## Run`: date (meta.created_utc), GPU (meta.gpu), model, git commit (meta.git_commit, plus a note if meta.git_dirty), upstream SHA, py-spy version, rate and flags, and the clock. Include one paragraph on instrumentation: numbers were taken with py-spy --nonblocking, gc.callbacks and tracemalloc active, so absolute latencies are higher than an uninstrumented run. Phase 7 measures uninstrumented, and this report is for attribution, not headline speed.
- `## Topology and GIL framing`: there are three processes (api_server with uvicorn; one tokenizer worker doing both tokenize and detokenize, because --num-tokenizer 0; and the scheduler), each with its own GIL. No cross-process GIL contention exists. Report GIL-held and CPU-active percentages per process, plus the tokenize vs detokenize bucket split inside the tokenizer process.
- `## Scenario 1: 128 concurrent agents with cancellations`, `## Scenario 2: 32-token short-prompt saturation` and `## Scenario 3: Cold start and host RAM`. Each gives:
  - requests (sent, completed, cancelled, failed, TTFT p50/p99 with every P99 written as f"{p99:.1f} ms", RPS);
  - GC per role (count, total pause ms, P99 pause);
  - the frontend and scheduler GC-to-P99 overlap rates for spike vs non-spike requests, with a one-sentence reading of whether frontend GC lines up with P99 spikes;
  - memory per role (RSS start/end/growth, tracemalloc peak, top 3 allocation sites) and tree RSS/PSS;
  - CPU per role (cpu_active_pct, gil_held_pct) and per-request ipc_zmq and serde ms for api_server and the tokenizer.
  Scenario 3 also gives hyperfine mean ± stddev, the self-timed ready seconds, and the tree PSS at ready.
- `## Radix cache share (input to RADIX-01)`: the share for each scenario as f"{share * 100:.2f}%", radix_samples / scheduler_samples, and a recommendation on RADIX-01's "meaningful share" condition. Label it as a recommendation for the author's decision, with the threshold reasoning stated.
- `## Inputs to Phase 7 benchmark design`: (a) the metrics Phase 7 must capture, each tied to a measured finding here (for example, frontend GC counts next to P99 if the overlap rates differ, tokenizer GIL-held % if it nears saturation in scenario 2, which makes BENCH-07's best --num-tokenizer run necessary, and tree PSS for scenario 3); (b) which effects can be credited to the frontend (api_server and tokenizer processes: IPC, serialization, tokenize/detokenize, HTTP stack, frontend GC) and which belong to the shared backend that both frontends pay (scheduler CPU, radix time, scheduler GC).
- `## Known blind spots`: native radix kernel time without --native, which counts inside its Python caller and cannot be split out; CUDA-sync spin time that py-spy counts as active scheduler time; py-spy sample drops under load, which make the percentages lower bounds; and the instrumentation overhead.
- `## Reproduce`: `bash scripts/gpu_phase2_profile.sh` plus the install line from Task 1.
