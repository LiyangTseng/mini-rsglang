<objective>
Make "an abort can never overtake its own submit" structural and prove it under concurrency (WIRE-03, success criterion 2).

Purpose: D-01 gives one FIFO path to the scheduler, but FIFO alone does not stop a racing task from enqueuing an abort before the submit it cancels. This plan adds `WriterHandle::abort(&Submitted)`. Only a completed `submit` produces a `Submitted` ticket, so every abort is enqueued after its submit by construction. D-02 requires a proptest of random concurrent submit/abort interleavings across many uids. D-03 requires it to run end to end through the real transport and a real mock-scheduler subprocess.

Output: `writer.rs` gains `abort` plus unit tests and a compile_fail doctest; `tests/ordering_proptest.rs` holds the deterministic cross-task tracer and the property test.

Choices (Claude's discretion per CONTEXT):
- Ticket API rather than a raw-uid abort. A raw-uid abort would need the writer to buffer or guess about submits that might never come.
- proptest case count is set after a timing spike (RESEARCH A4).
- Each case builds its own multi-thread tokio Runtime and calls `block_on`, the manual pattern RESEARCH recommends because the `proptest_async` crate targets async-std.
- 4 worker threads.
- Scenarios of up to 48 uids.

Requests that a client cancels before they are submitted (during tokenization) are not this layer's concern. Phase 5's FSM simply does not submit them. Document this on `abort`.
</objective>
