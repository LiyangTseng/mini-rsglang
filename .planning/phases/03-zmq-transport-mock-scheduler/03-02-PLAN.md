<objective>
Build the two transport components that the Phase 5 lifecycle FSM will sit on (WIRE-03):
- the single ordered writer: one thread owns the backend PUSH socket, fed by one FIFO queue (D-01);
- the per-uid reply dispatcher: one thread owns the detok PULL socket and routes every DetokenizeMsg to a bounded, drop-oldest channel registered for its uid (D-04, D-05, D-07).

Purpose: success criterion 1 says a request's token replies are routed back to it by uid. The tracer proves that end to end through the real mock-scheduler subprocess from 03-01. The expansion task proves bare-vs-batch coalescing and writer failure deterministically, and proves 32-way concurrent routing.

Output: `src/writer.rs`, `src/dispatch.rs`, `lib.rs` exporting both, and `tests/transport_e2e.rs`.

Choices made (Claude's discretion per CONTEXT):
- Writer mechanism: a dedicated OS thread fed by a bounded `tokio::sync::mpsc` (capacity WRITER_QUEUE_CAPACITY = 1024). This is the `tx-zmq` pattern in `.claude/CLAUDE.md` and RESEARCH Pattern 1.
- Per-uid channel: `tokio::sync::broadcast::channel(16)`, which overwrites the oldest entry and reports `Lagged(n)` (RESEARCH Pattern 2, Don't Hand-Roll). The consumer sees each overwrite as an in-band `UidEvent::Dropped(n)`, so no gap goes unsignaled.
- Dispatch table: owned exclusively by the dispatcher thread (`FxHashMap`). Registrations arrive on an unbounded control channel, which the dispatcher drains before routing each frame. The hot path has no lock. Correctness relies on tokio's `try_recv`, which waits for a send that is still in progress instead of reporting Empty (read in tokio 1.53.2 `sync/mpsc/chan.rs` `try_recv`, `TryPopResult::Busy`). Every completed `register` is therefore visible before the reply to its uid's later submit is routed.
- Dispatcher lifetime: it runs until every DispatchHandle clone is dropped, then drops its routes, which ends all live streams.

Plan 03-04 adds `WriterHandle::abort` (submit-ticket API) and the ordering property test. Plan 03-05 adds drop counters, `deregister`, stats and the backpressure tests.
</objective>

`submit` builds `BackendMsg::UserMsg { uid, input_ids, sampling_params }` and awaits `send`, mapping SendError to WriterClosed. dispatch.rs (D-04, D-05, D-07). Open with a module doc covering: the per-uid broadcast channel of capacity UID_CHANNEL_CAPACITY, a power of two so tokio's rounding keeps it at exactly 16, and fixed with no knob (D-07); drop-oldest instead of blocking; the drop is visible only to the consumer as `UidEvent::Dropped(n)` (RESEARCH Pitfall 4); unknown uids are dropped silently (D-04); the register-before-submit contract. Implement the names in the interfaces block.
- Private `enum Control { Register(i64, broadcast::Sender<TokenReply>) }`. DispatchHandle holds a `tokio::sync::mpsc::UnboundedSender<Control>`. `register` creates `broadcast::channel(UID_CHANNEL_CAPACITY)`, sends Register with the Sender, and returns `UidStream { uid, rx }`. A send error, meaning the dispatcher is gone, still returns a stream; it simply yields None.
- `UidStream::recv` awaits `rx.recv()` and maps `Ok(t)` to `Some(UidEvent::Token(t))`, `Err(RecvError::Lagged(n))` to `Some(UidEvent::Dropped(n))`, and `Err(RecvError::Closed)` to None.
- `spawn_dispatcher` spawns a thread named "rx-zmq" that owns the source and a `rustc_hash::FxHashMap<i64, broadcast::Sender<TokenReply>>`. Each iteration:
  1. Drain control with `try_recv`. Register inserts or replaces the route. Disconnected means every handle was dropped: log at debug and return, dropping all routes.
  2. Call `recv_detok(DISPATCH_POLL_MS)`. On Err, `tracing::error!` and return, which ends every live stream. On Ok(None), continue.
  3. On Ok(Some(bytes)), drain control again, then call `rsg_wire::decode_tokenizer`. A decode error is logged with `tracing::warn!` (the frame is skipped and the thread keeps running, never panicking). Otherwise route the message.

Routing recurses through BatchTokenizerMsg items in order. For a DetokenizeMsg, look up the uid:
- Missing: drop it.
- Present: `send` the TokenReply. If send errs (the receiver was dropped), remove the route. Otherwise, if finished is true, remove the route, which drops the Sender so the stream ends after its buffered events.

Never `.unwrap()` a decode result in either thread.
