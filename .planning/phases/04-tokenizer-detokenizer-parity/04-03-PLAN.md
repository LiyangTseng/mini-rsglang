  <behavior>
- Given a stream of ASCII tokens, each `step()` call returns the newly-decoded suffix text, concatenated across calls, equal to decoding the whole sequence at once.
- Given a token whose decoded text ends in the Unicode replacement character `\u{FFFD}` (an incomplete multi-byte sequence), `step()` withholds that text and instead applies `find_printable_text`'s CJK/last-space fallback, never panicking and never returning corrupted UTF-8.
- Given `finished=true` and `next_token == eos_token_id`, the EOS token itself is excluded from `decoded_ids` (per `detokenize.py`'s `if not (msg.finished and msg.next_token == self.eos_token_id)` guard), and the per-uid state is removed from the map afterward.
- Given a random `u32` token id outside the tokenizer's vocabulary range, `step()` returns a `Result::Err` or a safely-empty chunk — never panics (property, checked by Task 2's proptest).
  </behavior>
  <action>
Replace `detokenize.rs`'s placeholder with: `pub struct DecodeStatus { pub decoded_ids: Vec<u32>, pub
decoded_str: String, pub read_offset: usize, pub surr_offset: usize, pub sent_offset: usize }`
(the four Python fields plus `decoded_ids`, named identically to the Python dataclass). `pub struct
Detokenizer { tokenizer: tokenizers::Tokenizer, eos_token_id: u32, clean_up_tokenization_spaces: bool,
decode_map: std::collections::HashMap<i64, DecodeStatus> }` — use `std::collections::HashMap`, not
`rustc_hash::FxHashMap`: this phase's detokenizer runs only inside fixture-driven tests, not a live
request-keyed FSM under load, so introducing an additional unaudited crate (`rustc-hash` is not in
RESEARCH.md's Package Legitimacy Audit table either) for a non-functional perf concern is not
justified here; revisit in Phase 5 when a real live FSM exists, with its own audit at that time.
`impl Detokenizer { pub fn new(tokenizer: tokenizers::Tokenizer, eos_token_id: u32,
clean_up_tokenization_spaces: bool) -> Self; pub fn step(&mut self, uid: i64, next_token: u32,
finished: bool) -> Result<String, TokenizerError> }`. Port `detokenize()`'s per-call logic into
`step()`: insert a fresh `DecodeStatus` into `decode_map` on first sight of `uid`; append
`next_token` to `decoded_ids` UNLESS `finished && next_token == self.eos_token_id`; compute
`read_ids = decoded_ids[surr_offset..]` and `surr_ids = decoded_ids[surr_offset..read_offset]`; decode
both via `self.tokenizer.decode_batch(&[&read_ids, &surr_ids], false)` (`skip_special_tokens=false`,
matching upstream's `batch_decode` default); compute `new_text` as the suffix of the `read_ids`
decode AFTER the `surr_ids` decode's CHARACTER count (`surr_str.chars().count()`, never
`surr_str.len()`) — use `.chars().skip(n).collect::<String>()` or an explicit `.char_indices()`-based
byte offset, confirmed at a real char boundary; if `new_text` is non-empty and does not end with
`'\u{FFFD}'`, append it to `decoded_str`, advance `surr_offset = read_offset`, `read_offset =
decoded_ids.len()`; otherwise replace `new_text` with the `find_printable_text` fallback (ported
verbatim: ends-with-`\n` -> return as-is; last char is a CJK code point (`_is_chinese_char`, the
exact 8-range port) -> return as-is; second-to-last char is CJK -> drop the last char; otherwise
truncate at the last space, inclusive). If `clean_up_tokenization_spaces` is true (unused by Qwen3,
wired for Llama in Plan 04-06 — implement the chain now since it is cheap and self-contained), apply
it to `new_text`/`output_str` before appending. Compute the incremental output as the suffix of
`output_str` after `sent_offset` characters, update `sent_offset`, and on `finished`, `remove` the uid
from `decode_map`. Never `.unwrap()` a `decode_batch` call — propagate its `Result` through
`TokenizerError::Tokenizer`.

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Token-id stream -> `Detokenizer::step` | Any `u32` value, including out-of-vocab ids and adversarial sequences engineered to straddle multi-byte UTF-8 boundaries, can reach `step` once a live request path exists (Phase 5) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-04-06 | Denial of Service | `Detokenizer::step` (character-vs-byte slicing, `decode_batch` on out-of-vocab ids) | high | mitigate | Char-safe `.char_indices()`-based slicing (never a byte-length slice derived from another string's length, per Pitfall 1); `Result`-propagating `decode_batch` calls, no `.unwrap()`; a `proptest` property run against random/out-of-vocab `u32` sequences asserting no panic — this phase's own success criterion 3 names "no panics" explicitly, so this threat is mitigated inline in this plan's tasks, not deferred |
| T-04-SC | Tampering | cargo installs | high | mitigate | No new crates added by this plan (`proptest` was added and audited `OK` in Plan 04-01); `rustc-hash` is deliberately NOT added here (see Task 1's reversibility note) specifically to avoid an unaudited dependency for a non-functional concern |
