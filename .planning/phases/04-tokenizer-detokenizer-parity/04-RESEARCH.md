### Locked Decisions

- **D-01:** The Llama-3.x parity target is **Llama-3.2-1B-Instruct**. Tokenizer files are generally shared across sizes within a Llama version, so size doesn't weaken parity coverage; only the version (BOS handling, template shape) matters here. ## Summary

This phase ports three pieces of upstream Python logic to Rust, all read directly from `vendor/mini-sglang/python/minisgl/` this session: `TokenizeManager.tokenize` (chat-template render → `encode()`), `DetokenizeManager.detokenize`/`DecodeStatus` (the incremental-decode state machine), and `load_tokenizer()` (the HF asset-loading fallback chain). The Rust side uses the stack already pinned in `.claude/CLAUDE.md` — `tokenizers =0.22.2`, `minijinja`+`minijinja-contrib` 2.24.0 (`pycompat`), `hf-hub` 1.0.0 — and this session re-verified every one of those pins against the crates.io registry API and found no drift.

The two target models turn out to exercise almost disjoint feature sets. **Qwen3-0.6B** (`Qwen/Qwen3-0.6B`, confirmed as the exact HF repo id already used elsewhere in this repo) has `add_bos_token: false`, `bos_token: null`, `clean_up_tokenization_spaces: false` — none of TOK-04's named edge cases apply to it, so TOK-01/02/03 for Qwen3 reduce to "the Rust `tokenizers` core and the Python-wrapped same Rust core must agree," which is close to true by construction. Its chat template **does** have a tool-calling branch (`{%- if tools %}` ... `<tool_call>` rendering), resolving D-12 point 8: case 8 should be included. **Llama-3.2-1B-Instruct** carries essentially all of the hard cases: `add_bos_token: true` plus a template that itself emits `{{- bos_token }}`, `clean_up_tokenization_spaces: true` (requiring the Python-side `clean_up_tokenization` post-step, whose exact 10-replace body was read from `transformers` v4.57.3 source and is quoted below), and — newly surfaced by this research, not previously flagged in CONTEXT.md — a `strftime_now("%d %b %Y")` call that embeds **today's date** into the rendered prompt whenever `date_string` is not passed to `apply_chat_template` (which upstream's `tokenize.py` never does). This makes any committed Llama chat-template fixture date-sensitive unless the generator freezes the clock; see Pitfall 3 and Open Questions.

**Primary recommendation:** create a new `crates/rsg-tokenizer` library crate (auto-included by the workspace's `members = ["crates/*"]` glob) depending on `tokenizers`, `minijinja`+`minijinja-contrib`, `hf-hub`, `serde`/`serde_json`; load tokenizer assets with `Tokenizer::from_file` + raw JSON reads (never the `http` feature, which would pull a second `hf-hub 0.4.1`); hand-port `DecodeStatus` as a plain struct with the four Python fields read verbatim from `detokenize.py`; register `raise_exception` and `strftime_now` as native minijinja globals (neither is provided by `minijinja-contrib`); and freeze the clock when generating the Llama chat-template golden fixtures so `--check` doesn't go stale after the day it was generated.

## Architectural Responsibility Map

This project's architecture does not match the generic browser/SSR/API/CDN/DB tiers — it is a two-tier frontend/backend split per `.claude/CLAUDE.md`. Tiers below use the project's own vocabulary.

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Tokenization (text/messages → token ids) | Rust Frontend | — | CLAUDE.md: "Rust owns ingress, lifecycle FSM, tokenization, detokenization" |
| Chat-template rendering (messages → prompt string) | Rust Frontend | — | Same constraint; upstream's `tokenize.py` calls `apply_chat_template` before `encode()`, both inside the frontend process |
| Incremental detokenization (token stream → text chunks) | Rust Frontend | — | Same constraint; ports `DetokenizeManager`/`DecodeStatus` |
| Tokenizer/template asset resolution (`tokenizer.json`, `tokenizer_config.json`, `chat_template.json`, `special_tokens_map.json`) | Rust Frontend (via `hf-hub`) | Python/CUDA Backend | D-05/D-06: Rust fetches independently from the same `HF_HOME` cache the vendored `load_tokenizer()` also reads — both tiers must agree on tokenizer identity even though each loads it independently |
| Golden-fixture generation (parity oracle) | Python/CUDA Backend's frozen code, run standalone | — | D-07: a Mac-only CPython script imports upstream's own `tokenize.py`/`detokenize.py`/`hf.py` as ground truth; it does not reimplement them |

### Alternatives Considered
| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| Hand-rolled `DecodeStatus` port | `tokenizers::DecodeStream` | Rejected for parity. `DecodeStream` shares the *same* incomplete-UTF-8 heuristic as upstream (both check `string.ends_with('�')` / `new_text.endswith("�")`) `[CITED: raw.githubusercontent.com/huggingface/tokenizers v0.22.2 tokenizer/mod.rs]`, but it keeps only `(ids, prefix: String, prefix_index: usize)` — no `finished`+EOS exclusion, no `find_printable_text` CJK fallback, no per-`uid` map with explicit deletion on finish. It cannot reproduce `DecodeStatus` without being wrapped by the same logic anyway, so hand-porting the whole state machine is simpler than wrapping-then-patching `DecodeStream` |
| Raw `hf-hub` files (D-05) | A Python exporter dumping the effective `AutoTokenizer` state | Rejected by CONTEXT.md D-05: raw-file loading mirrors `load_tokenizer()` exactly; an exporter would be a second thing that can drift from upstream and the exporter itself would need parity-testing |
| `minijinja` native globals for `raise_exception`/`strftime_now` | Hoping `minijinja-contrib` supplies them | Does not exist: `minijinja_contrib::globals` only exposes `cycler`, `joiner`, `lipsum` (rand), `now` (datetime, UTC unix timestamp only), `randrange` (rand) `[CITED: docs.rs/minijinja-contrib/2.24.0]` — no `strftime_now`-equivalent formatter, no `raise_exception`. Both are official HF chat-template globals `[CITED: huggingface.co/docs/transformers chat_templating_writing]` and must be registered by hand |

### Pattern 1: hf-hub asset loading with the `load_tokenizer()` fallback chain
**What:** Port `vendor/mini-sglang/python/minisgl/utils/hf.py:load_tokenizer()` exactly: fetch `tokenizer.json` + `tokenizer_config.json` (+ `special_tokens_map.json` per D-06) via `hf-hub`; if `tokenizer_config.json` has no (or falsy) `chat_template` key, fall back to fetching `chat_template.json` and read its `"chat_template"` field.
**When to use:** Once per model, at process/test startup — not per request.
**Example:**
```python
# Source: vendor/mini-sglang/python/minisgl/utils/hf.py:17-27 — read directly this session
def load_tokenizer(model_path: str) -> PreTrainedTokenizerBase:
    tokenizer = AutoTokenizer.from_pretrained(model_path)
    # Some Mistral models store chat_template in a separate JSON file
    if not getattr(tokenizer, "chat_template", None):
        try:
            path = hf_hub_download(repo_id=model_path, filename="chat_template.json")
            with open(path, "r", encoding="utf-8") as f:
                tokenizer.chat_template = json.load(f)["chat_template"]
        except Exception:
            pass
    return tokenizer
```
```rust
// Rust port sketch — hf-hub 1.0.0 API confirmed via docs.rs this session
let client = hf_hub::HFClient::new()?; // reads HF_TOKEN / HF_HOME from env, same as Python
let repo = client.model(owner, name);
let tokenizer_json = repo.download_file().filename("tokenizer.json").send().await?;
let config_path = repo.download_file().filename("tokenizer_config.json").send().await?;
let config: serde_json::Value = serde_json::from_slice(&std::fs::read(&config_path)?)?;
let chat_template = match config.get("chat_template") {
    Some(v) if !v.is_null() && v != "" => v.as_str().unwrap().to_string(),
    _ => {
        // fallback: chat_template.json — mirror the try/except with a Result + ok()
        let ct_path = repo.download_file().filename("chat_template.json").send().await.ok();
        // ... read "chat_template" key, or leave None if the fallback also fails
    }
};
let tokenizer = tokenizers::Tokenizer::from_file(&tokenizer_json)?;
```

### Pattern 2: Chat-template rendering with required custom globals
**What:** `apply_chat_template(messages, tokenize=False, add_generation_prompt=True)` → render the Jinja template with `messages`, `add_generation_prompt=true`, and any special tokens the template references (`bos_token`, `eos_token`) as context values, exactly as upstream's `tokenize.py` call (no `tools`, `date_string`, or other kwargs are passed — confirmed by reading `tokenize.py` directly this session, lines 19-23 below).
**When to use:** Every request whose `msg.text` is a list (a chat conversation), per `tokenize.py`'s `isinstance(msg.text, list)` branch.
**Example:**
```python
# Source: vendor/mini-sglang/python/minisgl/tokenizer/tokenize.py:17-30 — read directly this session
if isinstance(msg.text, list):
    prompt = self.tokenizer.apply_chat_template(
        msg.text,
        tokenize=False,
        add_generation_prompt=True,
    )
    assert isinstance(prompt, str)
else:
    prompt = msg.text
input_ids: torch.Tensor = self.tokenizer.encode(prompt, return_tensors="pt")
```
```rust
// minijinja Environment setup — API signatures confirmed via docs.rs this session
let mut env = minijinja::Environment::new();
minijinja_contrib::add_to_environment(&mut env); // registers pycompat + filters + globals
env.set_unknown_method_callback(minijinja_contrib::pycompat::unknown_method_callback);
// Required HF globals NOT provided by minijinja-contrib — confirmed absent from
// minijinja_contrib::globals (only cycler/joiner/lipsum/now/randrange exist):
env.add_function("raise_exception", |msg: String| -> Result<minijinja::Value, minijinja::Error> {
    Err(minijinja::Error::new(minijinja::ErrorKind::InvalidOperation, msg))
});
env.add_function("strftime_now", |fmt: String| -> String {
    // Must match Python's datetime.now().strftime(fmt) byte-for-byte for the SAME instant;
    // freeze this in fixture generation (see Pitfall 3) — use `chrono`/`time` crate for prod.
    chrono::Local::now().format(&fmt).to_string()
});
env.add_template("chat", &chat_template_source)?;
let rendered = env.get_template("chat")?.render(minijinja::context! {
    messages => messages_value,
    add_generation_prompt => true,
    bos_token => bos_token_str,
    eos_token => eos_token_str,
})?;
let input_ids = tokenizer.encode(rendered, true)?; // add_special_tokens=true, HF default
```

### Pattern 3: Incremental detokenization — the exact upstream algorithm (verbatim)
**What:** The `DecodeStatus` state machine, read directly from `vendor/mini-sglang/python/minisgl/tokenizer/detokenize.py` this session. **This must be ported byte-for-byte, not reimplemented from a description.**
**When to use:** Per `uid`, once per `DetokenizeMsg` received, until `msg.finished`.
**Example (verbatim source, for exact porting):**
```python
# Source: vendor/mini-sglang/python/minisgl/tokenizer/detokenize.py:54-111 — read directly this session, quoted verbatim
@dataclass
class DecodeStatus:
    decoded_ids: List[int]
    decoded_str: str
    read_offset: int  # length of read ids
    surr_offset: int  # length of surr ids
    sent_offset: int  # length of sent out string

class DetokenizeManager:
    def detokenize(self, msgs: List[DetokenizeMsg]) -> List[str]:
        read_ids: List[List[int]] = []
        surr_ids: List[List[int]] = []
        for msg in msgs:
            if msg.uid not in self.decode_map:
                self.decode_map[msg.uid] = DecodeStatus(
                    decoded_ids=[], decoded_str="", read_offset=0, surr_offset=0, sent_offset=0,
                )
            s = self.decode_map[msg.uid]
            if not (msg.finished and msg.next_token == self.eos_token_id):
                s.decoded_ids.append(msg.next_token)
            read_ids.append(s.decoded_ids[s.surr_offset :])
            surr_ids.append(s.decoded_ids[s.surr_offset : s.read_offset])

        read_texts = self.tokenizer.batch_decode(read_ids)
        surr_texts = self.tokenizer.batch_decode(surr_ids)

        incremental_strs: List[str] = []
        for msg, read_str, surr_str in zip(msgs, read_texts, surr_texts, strict=True):
            s = self.decode_map[msg.uid]
            new_text = read_str[len(surr_str) :]
            if len(new_text) > 0 and not new_text.endswith("�"):
                output_str = s.decoded_str + new_text
                s.decoded_str = output_str
                s.surr_offset = s.read_offset
                s.read_offset = len(s.decoded_ids)
            else:
                new_text = find_printable_text(new_text)
                output_str = s.decoded_str + new_text

            incremental_output = output_str[s.sent_offset :]
            s.sent_offset = len(output_str)
            incremental_strs.append(incremental_output)
            if msg.finished:
                del self.decode_map[msg.uid]
        return incremental_strs
```

def _is_chinese_char(cp: int):
    if (
        (cp >= 0x4E00 and cp <= 0x9FFF)
        or (cp >= 0x3400 and cp <= 0x4DBF)
        or (cp >= 0x20000 and cp <= 0x2A6DF)
        or (cp >= 0x2A700 and cp <= 0x2B73F)
        or (cp >= 0x2B740 and cp <= 0x2B81F)
        or (cp >= 0x2B820 and cp <= 0x2CEAF)
        or (cp >= 0xF900 and cp <= 0xFAFF)
        or (cp >= 0x2F800 and cp <= 0x2FA1F)
    ):
        return True
    return False

def find_printable_text(text: str):
    if text.endswith("\n"):
        return text
    elif len(text) > 0 and _is_chinese_char(ord(text[-1])):
        return text
    elif len(text) > 1 and _is_chinese_char(ord(text[-2])):
        return text[:-1]
    else:
        return text[: text.rfind(" ") + 1]

**Rust port notes:**
- `batch_decode([read_ids], [surr_ids])` → `tokenizer.decode_batch(&[&read_ids, &surr_ids], skip_special_tokens=false)` — signature confirmed via docs.rs this session: `fn decode_batch(&self, sentences: &[&[u32]], skip_special_tokens: bool) -> Result<Vec<String>>`.
- The `"�"` check is `U+FFFD REPLACEMENT CHARACTER` — in Rust, `new_text.ends_with('\u{FFFD}')`.
- `read_str[len(surr_str):]` is a **Python string slice by character count**, not byte count. Rust must slice `read_str` starting at the **character** index equal to `surr_str.chars().count()`, not `surr_str.len()` (byte length) — a direct byte-slice would panic or corrupt multi-byte UTF-8 on CJK/emoji input. Use `.chars().skip(n).collect::<String>()` or compute the byte offset via `.char_indices()`.
- `del self.decode_map[msg.uid]` on `msg.finished` → the Rust `FxHashMap<u64, DecodeStatus>` must `.remove(&uid)` at the same point, or the per-request state leaks across the connection's lifetime (relevant to LIFE-01..03 in Phase 5, but the detokenizer's own map must not leak within this phase's tests either).

## Common Pitfalls

### Pitfall 1: Python string slicing is by character, not byte — a silent corruption/panic risk in the detokenizer port
**What goes wrong:** `read_str[len(surr_str):]` in Python slices by Unicode code point. A naive Rust port using `&read_str[surr_str.len()..]` slices by **byte offset**, which will either panic (`str` indexing requires a char boundary) or silently produce wrong text if it happens to land on a boundary byte that isn't the intended character boundary.
**Why it happens:** Rust `String`/`&str` indexing is byte-based by design (UTF-8 is variable-width); Python `str` indexing is code-point-based.
**How to avoid:** Compute the character count of `surr_str` and skip that many `char`s, or track byte offsets explicitly via `.char_indices()` and only slice at confirmed char boundaries.
**Warning signs:** A panic with "byte index N is not a char boundary" on any CJK or emoji fixture — this will surface immediately in TOK-03's CJK/emoji derived fixtures (D-09) if mishandled.

### Pitfall 2: The Llama double-BOS mechanism — now fully explained, not just named
**What goes wrong:** Llama-3.2-1B-Instruct's chat template begins with `{{- bos_token }}` (quoted from a third-party mirror of the gated repo's `tokenizer_config.json`, `[CITED: huggingface.co/unsloth/Llama-3.2-1B-Instruct tokenizer_config.json]` — the canonical `meta-llama` repo returned `401 Unauthorized` to this research session's unauthenticated fetch), while `tokenizer_config.json` also sets `"add_bos_token": true`. The rendered prompt string therefore **already contains** the BOS token text, and `tokenizer.encode(prompt, add_special_tokens=True)` (upstream's default, confirmed by reading `tokenize.py` directly) adds **another** BOS token on top — producing two BOS tokens in `input_ids` unless something de-duplicates.
**Why it happens:** the template and the tokenizer's own special-token insertion are two independent code paths in HF's design; Llama-family templates predate — or simply don't coordinate with — `add_special_tokens`.
**How to avoid:** D-10 already specifies the correct test (assert BOS appears **exactly once** in final `input_ids`). This research confirms *why* that assertion is the right one to write, and that it is Llama-specific — Qwen3 has `bos_token: null`, so this case cannot occur for Qwen3 and should not be tested there.
**Warning signs:** `input_ids[0] == input_ids[1] == bos_token_id` on any Llama fixture.

### Pitfall 3: `strftime_now()` makes Llama's rendered prompt date-sensitive — not previously documented in CONTEXT.md
**What goes wrong:** Llama-3.2-1B-Instruct's chat template contains `{%- set date_string = strftime_now("%d %b %Y") %}` guarded by `{%- if not date_string is defined %}` (quoted from the same mirror, `[CITED]`). Upstream's `tokenize.py` call to `apply_chat_template(msg.text, tokenize=False, add_generation_prompt=True)` passes **no** `date_string` kwarg (confirmed by reading `tokenize.py` directly — no such kwarg appears anywhere in the call), so the template always falls into the `strftime_now` branch and embeds **today's date** into the rendered prompt text. A golden fixture captured on one day and re-diffed by `gen_tokenizer_fixtures.py --check` on a later day will differ for a reason that has nothing to do with a real regression.
**Why it happens:** this is upstream's real behavior for Llama-family templates with no injected `date_string` — it is not a Rust-vs-Python bug, it is intrinsic non-determinism in the oracle itself.
**How to avoid:** the fixture generator must freeze the clock when generating Llama's chat-template fixtures — e.g. monkeypatch `datetime.datetime.now` (or register an overriding `strftime_now` global at render time) in `gen_tokenizer_fixtures.py` to a fixed instant, and the Rust test harness's `strftime_now` global must return the same fixed string during tests (production code can still call the real clock). This needs an explicit decision the planner should make — see Open Questions.
**Warning signs:** a previously-passing Llama TOK-02/04 fixture starts failing `--check` with only a date substring differing, on no code change.

### Pitfall 4: `tokenizers::DecodeStream` looks like a ready-made incremental decoder but is not a parity-safe substitute
**What goes wrong:** `DecodeStream::step(id) -> Result<Option<String>>` uses the same `'�'`-suffix heuristic as upstream (`string.ends_with('�')`, confirmed by reading the crate source this session) to detect incomplete UTF-8, which might suggest it can replace the hand-port. It cannot: it has no `finished`/EOS-exclusion branch, no `find_printable_text` CJK fallback for the "incomplete but not UTF-8-broken" case, and keeps only `(ids, prefix: String, prefix_index: usize)` rather than the four-field `DecodeStatus` upstream's batching semantics (`batch_decode` on `read_ids`/`surr_ids` pairs, not a single running decode) require.
**Why it happens:** `DecodeStream` solves a more generic "decode token-by-token without breaking UTF-8" problem; upstream's algorithm solves the more specific "match `batch_decode` semantics incrementally, with CJK and EOS special-casing" problem.
**How to avoid:** hand-port `DecodeStatus` as specified in Architecture Pattern 3. Do not attempt to wrap `DecodeStream` and patch in the missing branches — it saves nothing over porting the four fields directly, and invites divergence in the parts you *didn't* patch.
**Warning signs:** fixtures pass for ASCII streams but fail specifically on the "finished+EOS" case (D-09) or on CJK streams where `find_printable_text`'s "print until last space" fallback should have applied.

### Pitfall 5: `clean_up_tokenization` is a Python-side post-step, not inside the Rust `tokenizers` core — exact algorithm now confirmed
**What goes wrong:** assuming `Tokenizer::decode()` alone reproduces Python's `.decode()` output for Llama (`clean_up_tokenization_spaces: true`). The cleanup is applied by `transformers`' `PreTrainedTokenizerFast._decode()` **after** calling into the same Rust core (`self._tokenizer.decode(token_ids, skip_special_tokens=skip_special_tokens)`, confirmed by reading `tokenization_utils_fast.py` v4.57.3 directly), via `self.clean_up_tokenization(text)`, whose default resolves `kwargs.pop("clean_up_tokenization_spaces", False)` — so this step is skipped for Qwen3 (`false`) but required for Llama (`true`).
**Why it happens:** the Rust `tokenizers` core is shared, but the cleanup regex-like replace chain lives only in the Python `transformers` package, never ported into the Rust crate.
**How to avoid:** apply the exact 10-step chain, in order, only when the model's `tokenizer_config.json` sets `clean_up_tokenization_spaces: true`:
```python
# Source: github.com/huggingface/transformers v4.57.3 src/transformers/tokenization_utils_base.py
# `clean_up_tokenization` staticmethod — read directly this session, quoted verbatim
out_string = (
    out_string.replace(" .", ".")
    .replace(" ?", "?")
    .replace(" !", "!")
    .replace(" ,", ",")
    .replace(" ' ", "'")
    .replace(" n't", "n't")
    .replace(" 'm", "'m")
    .replace(" 's", "'s")
    .replace(" 've", "'ve")
    .replace(" 're", "'re")

```
Port as a chained `.replace(...)` sequence on a Rust `String`, in the exact same order (each `.replace` operates on the previous result).
**Warning signs:** Llama streamed-text fixtures differing only around apostrophes/contractions or punctuation-adjacent spaces.
