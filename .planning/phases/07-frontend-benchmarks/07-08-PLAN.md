<objective>
Add Scenario 3, frontend cold start and frontend memory with end-to-end startup reported separately (BENCH-05), to the shared orchestrator as a hyperfine-based single-trial runner (D-08).

Purpose: Phase 2 found that weight load and CUDA init dominate end-to-end startup (16.16 s uninstrumented hyperfine mean), so an end-to-end number alone would hide the frontend's share. This plan measures both, symmetrically for both frontends:
- end-to-end startup, timed by hyperfine
- the frontend's critical-path tail after the shared backend reports ready, from log-marker timestamps
- memory at ready, per role group and for the whole tree, with PSS on Linux (Phase 2 asked for tree PSS at ready separately from end-to-end PSS)

Output: scenarios/s3_coldstart.rs, procs.rs detach support, cmdline.rs shell quoting, the orchestrator's RunnerManaged branch, three subcommands (`s3`, `coldstart-once`, `coldstart-stop`) and tests.

Definition recorded (Claude's discretion; BENCH-05 does not define "frontend cold-start time"): the Python frontend's HTTP port only opens after the backend acks, so an HTTP-only probe cannot separate the frontend's startup from the backend's. The backend-ready marker can: the upstream launcher logs `Scheduler is ready` when it receives the scheduler ack, and the rsglang launcher logs `backend ready; handshake sent to rsg-server`. Both are "the launch process learned the backend is ready", the same event on both sides. The markers can be overridden per arm.
</objective>
