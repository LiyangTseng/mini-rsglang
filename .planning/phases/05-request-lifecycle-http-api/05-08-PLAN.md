<objective>
Turn the rsg-server binary into the real Rust frontend. It loads Phase 4's tokenizer, serves HTTP from startup, becomes ready when the backend's handshake arrives, and exposes the abort-timing and backend-timeout settings as server-wide CLI flags (D-01). Then let the launcher drive it, so `--frontend rust` serves the same port the user asked for. This is the binary Phase 6 runs on the GPU box.

Purpose: plans 05-01 through 05-07 proved the HTTP and lifecycle stack in-process, with a test codec. This plan swaps in the real tokenizer behind the same `TextCodec` seam and wires the stack into the process the launcher spawns. Plan 05-09 then byte-diffs that binary against the Python fixtures.

Output: `hf_codec.rs`, the new `main.rs` flow and flags, the `RsgServer` test harness, `tests/server_binary.rs`, the updated `tests/cli.rs` spawn args, and launcher host/port forwarding.

Choices made:
- The tokenizer loads before the handshake, in parallel with backend weight loading, so it never adds to end-to-end cold start (Phase 7 scenario 3). A load failure exits 1 before the server ever looks alive.
- The HTTP listener binds before the handshake, so `/health` answers as soon as the front half is up and `/health/ready` flips at the handshake. Generation endpoints and /v1/models return 503 until then, which preserves "first 200 on /v1/models means end-to-end ready" as in the Python frontend.
- New failure modes reuse EXIT_STARTUP (PATTERNS: allocate a new code only when separate diagnosis is needed).
- The launcher forwards host and port only. Forwarding --abort-timing through the launcher is left to Phase 6, which decides the benchmark setting; rsg-server's own flag (D-01) is complete here.
</objective>
