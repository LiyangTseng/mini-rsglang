<objective>
Serve the first full request on the Mac: a client POSTs /generate to the Rust HTTP layer, the request runs through a per-request lifecycle driver, out through Phase 3's single ordered writer to a spawned mock-scheduler, back through the per-uid dispatcher, through an incremental decoder, and out as upstream's single-newline `data:` framing. Then make the lifecycle explicit and checkable (LIFE-01): a pure transition table plus one registry actor that owns the table of live requests and counts every terminal exactly once.

Purpose: this is the tracer for the whole phase. It proves the architecture (axum ingress -> engine driver -> writer -> mock -> dispatcher -> decoder -> body stream) end to end before chat, cancellation, errors and observability expand it in later plans.

Output: `codec.rs`, `engine.rs`, `fsm/{mod,state}.rs`, `http/{mod,error,generate}.rs`, the shared HTTP test harness in `tests/common/`, and `tests/http_generate.rs`.

Choices made (Claude's discretion per CONTEXT):
- FSM shape. Phase 3 routes replies through per-uid UidStreams rather than one shared inbox, so each request gets its own driver task. That task is the single owner of the request's state. It reports every transition to one registry actor: a tokio task that owns `FxHashMap<i64, ReqState>` for live requests, with no locks on the hot path. The registry is the system-wide table for LIFE-01/LIFE-03 accounting. This adapts CLAUDE.md's "one task owns FxHashMap<u64, ReqState>" pattern to Phase 3's dispatcher. State names come from LIFE-01: Received, Tokenizing, Submitted, Decoding, Finished, Cancelled, Failed.
- Tokenizer seam. Phase 4 has no code yet, so the engine depends only on the `TextCodec` trait. Tests use a `ByteCodec` test double that lives in `tests/common/` (never in the production crate). Plan 05-08 plugs Phase 4's tokenizer into the binary behind the same trait. Encoding runs inline on the driver task: CLAUDE.md allows inline encoding for short prompts, and Phase 7 measures whether a dedicated pool is needed.
- `AbortGuard` lives in engine.rs, not in http/ as RESEARCH sketched. The engine hands it out inside `ActiveRequest`, and the engine must not depend on the http module. It wraps `tokio_util::sync::DropGuard`, so dropping the response body or the handler future cancels the request's CancellationToken. Plan 05-04 makes the driver act on that cancellation.
- All handlers read the raw body as `axum::body::Bytes` and deserialize with serde_json, mapping any error to 422. This mirrors FastAPI, which parses JSON even without a content-type header. A 16 MiB DefaultBodyLimit guards against oversized bodies.
- No tower-http and no tokio-stream: neither is needed. Body streams use `futures::stream::unfold`.
</objective>

codec.rs. Define the interfaces-block contract: ChatRole, ChatMessage, Prompt, CodecError, IncrementalDecoder, TextCodec. Module doc: this is the seam Phase 4's tokenizer plugs into (plan 05-08). `encode` mirrors upstream tokenize.py: Prompt::Text is encoded as is with special tokens added, and Prompt::Chat is rendered with the chat template (add_generation_prompt) and then encoded. `step` mirrors one DetokenizeMsg through DetokenizeManager.detokenize: it returns that message's incremental_output, possibly empty, with the EOS-on-finish exclusion.

engine.rs. Define the interfaces-block types. For Task 1, `Engine::new` takes writer, dispatch, codec and config; Task 2 adds the registry parameter. Engine holds `next_uid: AtomicI64` starting at 0. `start` allocates a uid with `fetch_add(1)`, creates a `tokio::sync::mpsc::unbounded_channel::<RequestEvent>()` and a `tokio_util::sync::CancellationToken`, wraps `token.clone().drop_guard()` in `AbortGuard`, `tokio::spawn`s the driver, and returns `ActiveRequest { uid, events, guard }`. The channel is unbounded on purpose: a slow HTTP client must never stall the driver, which would make the dispatcher overwrite this uid's tokens. Memory per request is bounded by its max_tokens, which the scheduler clamps to max_seq_len.

Driver (an async fn owning the request), happy path:
1. Encode the prompt with the codec. On Err, send `Rejected(SubmitError::Codec(msg))` and stop.
2. `dispatch.register(uid)` before submitting (Phase 3 contract).
3. `writer.submit(uid, Tensor::from_i32_slice(&ids), params).await`. On WriterClosed, `dispatch.deregister(uid)`, send `Rejected(SubmitError::BackendUnavailable)` and stop.
4. Send `Accepted`, create `codec.decoder()`, then loop on `stream.recv().await`:
   - `UidEvent::Token(r)`: `decoder.step(r.next_token, r.finished)`, then send `Token { text, finished: r.finished }`, and stop after the finished token (the dispatcher already removed the route). On a decoder Err: deregister, abort with the Submitted ticket, send `Failed(RequestError::Decode(msg))` and stop.
   - `UidEvent::Dropped(n)`: deregister, abort with the ticket, send `Failed(RequestError::SlowConsumer { dropped: n })` and stop. A gap would corrupt the decoded text, so the request fails instead of streaming wrong output.
   - `None`: send `Failed(RequestError::BackendGone)` and stop.

Ignore send errors on the events channel (the receiver may be gone). Log with tracing at debug/info using only uid, input_len and max_tokens; never log prompt or output text. Leave a doc comment on the driver noting that plan 05-04 adds cancellation, abort timing, the backend timeout and the overlong check. `ActiveRequest::accepted` awaits the first event: Accepted gives Ok, Rejected(e) gives Err(e), and a closed channel gives Err(SubmitError::BackendUnavailable). Any other first event is a bug (`unreachable!` is not allowed; return Err(BackendUnavailable) and log at error).

2. Call `state.engine()?`.

   - a closed channel before the finished token also yields an io error.
