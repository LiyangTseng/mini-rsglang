<objective>
Make cancellation and failure real. A client disconnect turns into an abort on the backend: immediately by default, or deferred until the first token under `--abort-timing deferred`. Late tokens after an abort are dropped and counted. An overlong prompt gets an immediate 400, and a backend that stops responding times out with an error instead of hanging.

Purpose: success criteria 2 and 4 (LIFE-02, LIFE-04, LIFE-05), plus the measured bound on hyper's disconnect detection that STATE.md lists as an open question and D-03 accepts as a documented limitation.

Output: the cancellation, timeout and overlong paths in `engine.rs`; the D-03 documentation on `AbortGuard`; `tests/http_cancellation.rs`, `tests/abort_timing.rs` and `tests/http_errors.rs`.

Choices made (Claude's discretion per CONTEXT):
- Backend timeout: an inactivity deadline of `EngineConfig.backend_timeout`, armed at submit and re-armed after every token. On expiry the driver deregisters, sends an abort so the scheduler frees the request, and fails the request:
  - streaming: the body ends with an io error, so hyper drops the connection without a terminating chunk, and there is no [DONE];
  - non-streaming: 504 backend_timeout (mapping already in ApiError).
  The production default is DEFAULT_BACKEND_TIMEOUT_MS (60 s). Plan 05-08 exposes it as `--backend-timeout-ms`; tests use a few hundred ms.
- Overlong check: after tokenization, against the handshake's max_seq_len, with the scheduler's own rule (`input_len >= max_seq_len` is dropped, scheduler.py:177-188). Everything the scheduler would silently drop gets a 400 instead, and nothing shorter is rejected.
- Cancellation is observed by a `biased` tokio::select! with the cancellation branch first, so an abort goes out promptly even while tokens are streaming. If a finished token and a cancellation race, whichever the driver observes first decides the single terminal state. An abort for an already-finished uid is a no-op at the scheduler (scheduler.py:190-195).
- SSE keep-alive comments are not added (CONTEXT left them optional). The queued-disconnect test below measures how long a queued request survives a disconnect under D-03.
</objective>

<assumption_delta_decision>
Signal: "Abort timing is configurable" (derived -> chosen). Upstream derives abort timing implicitly: it polls `is_disconnected()` and sleeps 100 ms before the abort. Here it becomes a chosen, server-wide setting (D-01). Decision: add alongside, do not promote. Immediate stays the default path and the deferred path is a second branch inside the same driver, selected once per process by `EngineConfig.abort_timing`. It is never a per-request field, and no existing contract (wire format, HTTP API, the Phase 3 writer/dispatcher) changes shape. Reversibility: costly (per D-01). Phase 6's fair A/B comparison depends on one global mode per run, so a later move to per-request control would mean redesigning how Phase 6/7 drive both frontends symmetrically.
</assumption_delta_decision>

## Flagged assumptions (spec-less edge probe)

These probe rows were `unclassified` and stay `unresolved`; the plan records the semantics it implements so the verifier can review them:
- LIFE-02 (unclassified): for non-streaming requests and requests still queued without a write, "immediately" is bounded by hyper's disconnect detection. Per D-03 the bound is accepted and measured (`queued_stream_disconnect_abort_bound` here, the non-streaming test in plan 05-07), not engineered away.
- LIFE-05 (unclassified): deferred mode sends no abort when the client goes away before submit (nothing reached the backend), and none when the first token is also the final one (the backend already finished). It aborts at the backend timeout if no first token ever arrives, and records every such request as Cancelled, not Failed.
