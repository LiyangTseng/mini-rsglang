<objective>
Add the rest of the upstream-parity surface: /v1/chat/completions (streaming and non-streaming), /v1/models and /v1, with byte-level framing and JSON formatting taken from upstream's api_server.py.

Purpose: API-01 requires these endpoints to behave identically to the Python frontend. The authoritative proof is plan 05-09's diff against fixtures captured from a live Python-frontend run (D-02). This plan builds the routes from the verbatim upstream source, and pins the formatting rules that are easy to get wrong with byte-level tests:
- streaming chunks use Python's json.dumps defaults (ensure_ascii, `", "`/`": "` separators), while non-streaming bodies are compact JSON without ASCII escaping (Starlette's JSONResponse);
- streaming ids are `cmpl-` and non-streaming ids are `chatcmpl-`;
- the object tag is `text_completion.chunk`;
- usage is all zeros and finish_reason is always "stop".

Output: `http/pyjson.rs`, `http/chat.rs`, `http/models.rs`, router registration in `http/mod.rs`, and `tests/http_chat.rs` plus `tests/http_models.rs`.

Choices made (Claude's discretion):
- Streaming chat uses the same manual `Body::from_stream` framing as /generate, not axum's built-in SSE type (CLAUDE.md allows "byte-identical manual framing"). Two reasons: the content-type must match Starlette's `text/event-stream; charset=utf-8`, and keep-alive comments would break byte parity. Keep-alive is therefore not implemented (CONTEXT left it optional).
- Every upstream route returns 503 not_ready until the engine is set. That keeps "first 200 on /v1/models" equivalent to "end-to-end ready", which matches the Python frontend: it does not listen at all until the backend is up.
</objective>
