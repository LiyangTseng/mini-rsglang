<objective>
Add the three operational routes API-02 requires (`/health`, `/health/ready` and a minimal `/metrics` with the request count, cancellation count and a TTFT histogram), fed by the lifecycle registry so the numbers come from the same single-owner table that proves exactly-once termination.

Purpose: success criterion 5. These routes have no upstream equivalent, so their shape is this phase's own design (RESEARCH: "free design space"). Phase 7's harness and Phase 6's GPU runs can read them.

Output: `metrics.rs`, `http/health.rs`, metrics recording in the registry actor, `AppState` holding the metrics, and `tests/observability.rs`.

Choices made (Claude's discretion per CONTEXT: label cardinality and TTFT buckets):
- No labels on any series. Cardinality stays constant regardless of traffic, and nothing request-specific (uid, model text, prompt) can leak into the metrics.
- TTFT buckets, in seconds: 0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10, 30.
- A per-server `PrometheusRecorder` from `metrics-exporter-prometheus`, never installed as the process-global recorder. Handles are registered once through the `metrics::Recorder` trait and kept in `ServerMetrics`. This keeps in-process test servers running in parallel isolated from each other, and keeps the exposition format out of hand-written code (RESEARCH "Don't Hand-Roll").
- `/health` means "process alive" and is always 200. `/health/ready` means "readiness handshake received, engine set". This front-half/end-to-end split is what Phase 7's cold-start scenario measures.
</objective>
