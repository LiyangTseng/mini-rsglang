Root causes, re-verified by direct code read during planning:
- G-01-8 / WR-01 (python/rsglang/launch.py:100-126): run_rust_mode calls resolve_rust_bin (L104) and returns 2 on a missing binary (L105-106) before _run_rust_mode calls parse_args (L123), which yields the authoritative run_shell flag that catches abbreviations. Reproduced on the current code: `--frontend rust --rust-bin /nonexistent/rsg-server --shell-m --model M --dtype bfloat16` prints only "rsg-server binary not found; run: cargo build -p rsg-server" and exits 2. On a first run, before `cargo build`, the user is told to build the binary when the real problem is that shell mode is unsupported in rust mode.
- G-01-9 / IN-01 (python/rsglang/backend.py:81-97): the prctl try block only catches OSError (L92). The `libc.prctl.argtypes = [...]` assignment (L83) does a ctypes symbol lookup, and an unexported prctl symbol raises AttributeError. Reproduced on the Mac, where the real `ctypes.CDLL(None).prctl` raises "AttributeError: dlsym(RTLD_DEFAULT, prctl): symbol not found", and a forced `sys.platform = 'linux'` child dies with that traceback instead of degrading. The exception still reaches the launcher as an error envelope through run_scheduler's outer except BaseException, but the scheduler is aborted. That defeats WR-06's guarantee (01-10) that a PDEATHSIG failure logs and degrades to the polling watchdog.

Purpose: D-05 says rust mode must reject shell mode however it is spelled, and the user should see the real reason. D-12 says the watchdog backstop must never itself abort the scheduler.
