## Deferred Items

- One unexplained slow e2e failure (1 in about 110 runs of python/tests/test_launch_rust_e2e.py)
  status: open
  **What:** During 01-05, one run of the e2e suite failed and took about 10 s longer than usual. That matches the launcher's 10 s shutdown grace followed by the group SIGKILL escalation, which happens when a child ignores SIGINT for 10 s. At the time the failure tests asserted an exit code of exactly 1. The output was not captured, so the failing test is unknown. It did not recur in about 110 more runs (sequential, targeted, and two concurrent loops). Two hypotheses were tested and ruled out: (1) SIGINT not interrupting a blocking zmq `socket.poll` in the fake's peer probe, which in fact interrupts within 0.1 s, and (2) the new watchdog thread absorbing SIGINT, where masking made no difference. The failure tests now assert a non-zero exit, as the plan specifies: 1, or -9 when escalation was needed. Both outcomes satisfy D-12. The tracer test still asserts exit 0 on SIGTERM. If it ever fails with -9, its assertion message contains the full launcher stderr, so look for `escalating to SIGKILL`.
- Launcher already leads its process group inside an interactive shell pipeline (`... | tee log`)
  status: open
  **What:** Carried from 01-03. In that case `killpg` also signals the other pipeline members (for example `tee`), and the SIGKILL escalation would kill them too. 01-05 made every launcher stderr write tolerate a closed or broken stderr, so shutdown always completes. The signalling of pipeline siblings remains. Workaround: run the launcher under `setsid`, or redirect to a file instead of piping, as scripts/gpu_phase1_check.sh does. A real fix would give the children their own process group distinct from the launcher's. That changes D-12's "launcher's group" design, so it needs a decision.
